# OPTIMIST LUDO — стратегия бесплатного размещения

## Цель MVP

Запустить небольшую публичную бету без платных внешних голосовых сервисов и без обязательных платных баз данных. Архитектура должна оставаться простой для одного небольшого Node.js-процесса.

## Что запускаем

- Один Node.js backend: HTTP API + WebSocket в одном сервисе.
- Один авторитетный игровой процесс для комнат и ходов на первом этапе.
- Открытие Mini App через URL, настроенный в BotFather. Отдельный webhook для команд `/start` и `/help` в текущем релизе 2.0 не реализован и нужен только при отдельном требовании к ответам бота в чате.
- Статические файлы Mini App и оптимизированные WebP-ассеты.
- Временный bounded RAM cache для голосовых сообщений по схеме из OPTIMIST DURAK.
- Ограниченную историю комнатного и общего текстового чата.

## Чего не подключаем на старте

- LiveKit, WebRTC и постоянные голосовые комнаты.
- Redis и отдельный pub/sub-кластер.
- Отдельный media server.
- Платные CDN и платное object storage.
- Микросервисы ради функций, которые можно безопасно обслужить одним процессом.

## Ограничения и честные компромиссы

1. Бесплатные тарифы хостингов отличаются по поддержке WebSocket, лимитам часов работы, RAM, диску, входящему трафику и правилам сна. До выбора провайдера проверяем условия его текущего бесплатного тарифа; название провайдера нельзя зашивать в архитектуру.
2. Если хост засыпает, активные WebSocket-соединения разрываются. Клиент должен переподключаться и получать полный снимок комнаты. Для обычного обрыва внутри того же процесса используется ограниченный по времени room-bound resume token; при перезапуске процесса токены и комнаты всё равно теряются и требуется новая Telegram-авторизация/новая партия.
3. Если процесс перезапустился, in-memory комнаты и RAM-кэш голосовых теряются. Для сохранения партии после перезапуска нужно сохранять authoritative snapshot в постоянное хранилище. В первой бесплатной бете это отдельный критерий/ограничение, а не обещание «бесконечного» восстановления.
4. Не используем keep-alive обходы, нарушающие правила бесплатного тарифа. Выбираем тариф, где допустима наша модель нагрузки.
5. Несколько backend-инстансов пока не запускаем: in-memory комнаты, голосовые файлы и чат не синхронизированы между процессами. Для горизонтального масштабирования позже понадобятся общий state store/pub-sub и совместимое хранилище.

## Минимальная защита от расхода ресурсов

- Ограничение частоты сообщений и игровых команд.
- Ограничение длины текста (200 символов для чата MVP).
- Ограничение голосового файла (512 KiB, до 30 секунд).
- Общий лимит RAM под голосовые файлы (8 MiB) и максимум 40 файлов на процесс.
- TTL голосовых файлов 6 часов и периодическая очистка.
- История до 50 сообщений на комнату.
- Не более 100 WebSocket-соединений на процесс и 4 одновременных загрузок голосовых. Это защитные стартовые лимиты, а не обещание такой производительности на любом free-тарифе.
- Ограничение числа одновременно открытых комнат (по умолчанию 20) и игроков конфигурацией сервера.
- Максимальный размер WebSocket frame; голосовые байты через WebSocket не передавать.
- Кэширование и сжатие статических ассетов; Board-Token WebP готовить в малых размерах.

## Персистентность

Профили, настройки и рейтинги нельзя надёжно хранить только в RAM. Перед публичным релизом выбираем одно из двух:

- бесплатная managed database с подходящими лимитами и понятной политикой сна/удаления;
- SQLite на persistent disk, только если выбранный хост действительно предоставляет постоянный диск на бесплатном тарифе.

Для live-матчей можно сохранять снимок состояния после каждого подтверждённого действия. Тогда после рестарта игроки могут восстановить матч, если сохранённый snapshot ещё актуален. Если подходящего постоянного хранилища нет, бета честно сообщает, что рестарт сервера может завершить текущие матчи.

## Этапы включения нагрузки

1. Локальная проверка одного стола и голосовых сообщений.
2. Закрытый тест 2–5 комнат, ограниченные голосовые лимиты.
3. Публичная бета с мониторингом RAM, CPU, WS disconnects, времени ответа и cache evictions.
4. Увеличение лимитов только по результатам метрик и после проверки ограничений выбранного хостинга.

## Условие выбора хостинга

Провайдер должен явно поддерживать Node.js HTTP + WebSocket на нужном тарифе, разрешать требуемое время работы и иметь достаточный лимит RAM. Если бесплатный тариф засыпает или не поддерживает WebSocket, он не подходит для активной real-time игры без изменения архитектуры.

## Тестовое размещение на Render

В корне репозитория добавлен `render.yaml` для создания Web Service из GitHub Blueprint. Он задаёт Node 22, команду `npm start`, health check `/healthz` и параметры production-режима. `BOT_TOKEN` и `ALLOWED_ORIGINS` намеренно помечены `sync: false`: после создания сервиса их нужно заполнить в панели Render вручную. В `ALLOWED_ORIGINS` указывается только точный HTTPS origin созданного сервиса, например `https://<service>.onrender.com`, без завершающего слеша. Затем тот же URL нужно задать для Mini App в BotFather.

Blueprint подготавливает конфигурацию, но сам по себе не создаёт Telegram-бота, не получает его токен и не публикует приложение в аккаунте пользователя. До заполнения обоих секретных значений production-сервер не запустится — это намеренная защита, а не ошибка сборки.
